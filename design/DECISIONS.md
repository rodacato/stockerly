## Decisions to make (design calls)

| **D1** | Palette values for the `@theme` token contract | Muted fresh values · Code's Lumen values | ✅ **Adopt the code's Lumen palette (reused contract, code's values).** First tried muted "fresh" values (ink-blue `#2B4B6F`); Adrian found them conservative and preferred the code's brighter, more cheerful indigo (`#5B6CFF`) + colorful semantics. So **design and code converge on color** — the color revamp becomes a no-op. The modern/youthful feel comes from **type + shape**, not a bespoke palette: display = **Plus Jakarta Sans** (the code's), **rounder radii** 8/12/16/20. Light+dark lifted from `app/assets/tailwind/application.css`. Reverses the earlier "fresh values" call — 2026-08-23. |
| **D2** | Charts: how to render them | TradingView iframe · `lightweight-charts` (OSS) | ✅ **`lightweight-charts` (TradingView's MIT lib), our data.** An iframe leaks the watchlist to a third party (breaks self-hosted/outbound-only ethos), can't show MXN/historical-FX, is heavy and unbrandable. The OSS lib renders our own series, self-hostable via importmap. Iframe stays a fallback only for a chart type we can't render (unlikely). Recommended 2026-08-23. |
| **D3** | Confluence "3-light" (`semáforo`) — the distilled signal | — | ⏳ **Open (design only; build gated).** Design the full target; Light 1 (RSI<30 & below lower BB / RSI>70 & above upper BB) and Light 3 (MA/MACD trend change) are groundable from existing observations; Light 2 + the time-window are net-new and render as "próximamente". The **engine** waits on a 4-filter discovery card before any build. See `flows/cockpit.pen` brief + `../redesign/design/prompts/02`. |
| **D4** | Responsive: how to handle mobile + desktop | Every screen ×2 · Mobile-first + selective desktop | ✅ **Mobile-first is canonical (390×844). A desktop artboard is drawn ONLY when the layout genuinely diverges (Setup split-panel; cockpit/asset-detail master-detail), when Adrian requests it, or when a dense screen needs its distribution checked.** Everything else reflows (`max-w` centered) via Tailwind — mobile artboard + a one-line desktop note in the brief, no separate artboard. `AppShell`/nav is the one component with two variants (mobile bottom-tab vs desktop top/side). Confirmed with Adrian 2026-08-23. |

Structure/layout/UX are ours; grounding is the code's. |
| **D9** | How the Activos tab expresses interest in a symbol | Two lists (own / follow) · **Three tiers** · Three peer tabs | ✅ **Three tiers, drawn as a ladder — not as three peer tabs.** Adrian pushed back on the first two-list draft and he was right: the code already runs a three-level priority ladder, and the level decides where a scarce budget goes. `Asset.syncing` (**Rastreado**) gets daily price + trend score; `watchlist_items` (**Sigo**) gets priority 1 on fundamentals/statements and drives watchlist sentiment, news and earnings filters; open `positions` (**Poseo**) get priority 0 **and are the only tier whose dividends and splits are synced at all** ([`sync_dividends_job.rb:36`](../app/jobs/sync_dividends_job.rb#L36), [`sync_splits_job.rb:44`](../app/jobs/sync_splits_job.rb#L44)). The ordering is literal SQL in [`sync_all_fundamentals_job.rb:36-45`](../app/jobs/sync_all_fundamentals_job.rb#L36-L45), capped at `DAILY_BUDGET = 25` Alpha Vantage calls/day. **Shape:** the segmented control stays at two (`Cartera | Sigo` — the two daily questions); `Rastreados` is a foot-of-list entry with its own screen, where the budget is visible and sync can be paused. Crossing a tier is one tap, in both directions, and states what you gain. Naming per S4 Camila: **"Rastreados"** (the code's own word), never "Radar" — that name is already the Panorama list. 🐞 **App bug this exposes:** [`dashboard/_watchlist_table.html.erb`](../app/views/dashboard/_watchlist_table.html.erb) titles the watchlist **"Tus posiciones"** while real positions live in `/portfolio` — the confusion the beta reported. Fix rides the Activos revamp (CODE_CHANGES §4). Decided 2026-08-24 (panel: C6 Esther, S2 Adriana, C5 Renata, C1 Lucía, S4 Camila, C4 Marisol).
| **D10** | How money is written when MXN and USD appear in the same view | Bare `$` · ISO prefix everywhere · Normalized list + prefix on exceptions | ✅ **A list declares its currency once in the section header and drops the symbol from every row (`52,400`); any value NOT in the declared currency carries an explicit ISO prefix (`USD 172.40`).** A bare `$` across a mixed MXN/USD portfolio is precisely the ambiguity the multi-currency P0 exists to kill, and repeating `MXN` on every row is noise. Matches the code's `format_currency_mx` (ISO prefix, `app/helpers/dashboard_helper.rb:17`) rather than inventing a format. **Consequence, since resolved:** `cockpit.pen` was painting bare `$38,000`; it got its pass on 2026-08-24 — the Radar subtitle now declares MXN, rows dropped the symbol, and the position grid (which genuinely mixes MXN and USD) carries explicit ISO prefixes. Decided 2026-08-24. |
| **D11** | The trade sheet on a real mobile browser | Bottom sheet as drawn · Full-screen form · **Sheet with a sticky footer** | ✅ **Route first, drawer as the presentation.** `/trades/new` is a real URL that renders a full page on its own; navigating to it from the Activos list loads it into a Turbo Frame with `data-turbo-action="advance"` and paints it inside a native `<dialog>` styled as the bottom sheet. This is what makes the drawer affordable: the **back button closes it for free** (the URL really changed — a pure JS drawer either hijacks history or drops the user out of the app, the worst failure on a mobile browser), and if the JS never runs the form is still a working page. Desktop shows the same `<dialog>` centered (D4). **And it is built for the keyboard, not for the mockup.** A `position: fixed; bottom: 0` drawer anchors to the *layout* viewport, so iOS Safari's keyboard covers its lower half — including the submit button — and the 664pt sheet does not fit the ~553pt left above the keyboard. Rules: (a) `max-height: 85dvh` (`dvh`, not `vh` — the address bar collapses), (b) the field area scrolls internally while a **sticky footer keeps Total + Guardar always visible**, (c) reposition on `visualViewport` `resize`/`scroll` rather than trusting `bottom: 0`, (d) `padding-bottom: env(safe-area-inset-bottom)`, (e) native `<dialog>` for the backdrop + focus trap, (f) native `<input type="date">` and `inputmode="decimal"` — no custom pickers, (g) no drag-to-dismiss: the grabber is an affordance, the X and the backdrop are the real exits. Desktop (D4) reuses the same `<dialog>` centered. The `Con teclado` artboard is the spec, not the clean one. Cost of the drawer over a plain page: one `<dialog>` + ~30-line Stimulus controller; the design does not change either way — the same artboards read as a full page. Raised by Adrian 2026-08-24, resolved same day. |
| **D12** | The Consolidado's "¿Valió la pena?" comparisons | Drop them · Design + build now · **Design now, gate the engine** | ✅ **Design the full target; the engine is build-gated behind a 4-filter card, same treatment as D3.** The *data* is all there — `PortfolioSummary` (FX-historical cost basis), daily `portfolio_snapshots`, `PeriodReturnsCalculator`, allocation by type/sector, and **`BanxicoGateway` already fetches CETES auction rates** (`CETES_SERIES`, `fetch_auctions`), so the benchmark needs no new gateway. What is missing is the counterfactual calculation, and one thing more serious. 🔴 **`PeriodReturnsCalculator` measures money-weighted return** — it diffs the current total against an older snapshot ([`period_returns_calculator.rb:52-60`](../app/contexts/trading/domain/period_returns_calculator.rb#L52-L60)), so depositing cash and buying more makes the "return" rise while nothing performed better. Comparing *that* against CETES would state a falsehood on the one screen whose entire job is "did this beat doing nothing". **The comparison cards require time-weighted return (TWR); the existing period figures cannot be reused for them.** Snapshots carry `cash_value` and `invested_value`, so the flows needed to derive TWR are recoverable. Logged 2026-08-24. |

# 2.0 cutover — production runbook

> # ⛔ EXECUTED 2026-08-23 — HISTORICAL. DO NOT RE-RUN.
>
> **This is a spent one-time runbook, kept only as the record of how the 2.0 cutover happened.**
> Step 2 is `DROP DATABASE stockerly_production`. Running it today destroys the live single-user
> database — every trade, alert and encrypted provider key — and there is no backup step anywhere in
> this document, by design: at the time there was nothing worth keeping.
>
> Nothing here is a live procedure. For a normal deploy see [`deploy.md`](./deploy.md). Its branch
> preconditions no longer exist and its API-key steps describe a schema that has since been dropped;
> both are annotated inline below.

One-time cutover of `stockerly.notdefined.dev` (andys-room) from the failed multi-user beta to the
single-user 2.0. **Nothing in production was being preserved** — the beta data was expendable, so
the DB was wiped and the app booted fresh into the first-boot setup wizard.

## Preconditions (as they stood at execution time)

- `evolve_2_0_pre` is green (rspec, rubocop, brakeman, bundler-audit) and merged to `master` via PR.
  **The branch no longer exists** — it was deleted after the merge; the 2.0 work is on `master`.
- You have Kamal access to andys-room (SSH via Tailscale + the deploy secrets in your shell / `.kamal/secrets`).
- Encryption + DB secrets are already set in the `production` GitHub Environment (they powered the
  beta), so no new secret wiring was needed.

## Steps

### 1. Land the branch on the deploy line
- Merge PR `evolve_2_0_pre → master` (CI green). *(Branch since deleted.)*
- Fast-forward the deploy branch to master and push it — the deploy workflow triggers on push to
  `production`:
  ```bash
  git fetch origin
  git checkout production && git merge --ff-only origin/master && git push origin production
  ```
  (Or trigger `deploy.yml` manually via `workflow_dispatch` with action `deploy`.)

### 2. Wipe the production database (the one deliberate, irreversible step)

> ⛔ **This step already ran on 2026-08-23.** It is transcribed, not offered. Do not paste it.

The app entrypoint runs `bin/rails db:prepare` on boot, so an **empty** DB is rebuilt to the current
schema automatically. `db:prepare` will *not* wipe an existing DB — so we drop + recreate it empty.
Run from a machine with Kamal access:
```bash
# Stop the app so no connections block the DROP
bin/kamal app stop

# Drop + recreate an empty database (connect to the maintenance `postgres` db)
bin/kamal accessory exec postgres --interactive \
  'psql -U stockerly -d postgres -c "DROP DATABASE IF EXISTS stockerly_production; CREATE DATABASE stockerly_production OWNER stockerly;"'
```
The Solid Queue / Cache / Cable databases are separate (`*_queue`, `*_cache`, `*_cable`); if they
carry stale beta state, recreate them the same way — otherwise `db:prepare` handles them.

### 3. Deploy
If step 1 already pushed `production`, the deploy is running. Otherwise deploy now:
```bash
bin/kamal deploy
```
On boot the entrypoint's `db:prepare` loads the fresh schema and runs migrations → empty single-user
DB. The `job` role (Solid Queue worker) comes up alongside `web`, so background sync runs in prod.

`config/deploy.yml` sets `SOLID_QUEUE_IN_PUMA: false` in production deliberately: the worker is its
own Kamal role with its own container, and letting Puma also supervise Solid Queue would run the
queue twice. It is a production setting, not a local-dev one.

### 4. First boot
- Open `https://stockerly.notdefined.dev` → no users → redirected to `/setup`.
- Create the single account. `CreateFirstAdmin` bootstraps the platform (integrations, market
  indices, FX) and creates your portfolio + alert preferences.
- In the onboarding wizard (or later in **Admin > Integrations**), add your provider API keys.

  > **Superseded.** This step originally described **multiple keys per provider** rotated by
  > `api_key_pool` to stretch free-tier limits. [ADR-015](../architecture/adr/0015-one-api-key-per-provider.md)
  > retired that, and `db/migrate/20260826150000_move_api_key_onto_integrations.rb` moves the key
  > onto `integrations` and drops the `api_key_pools` table. It is **one key per provider** now.
- Launch → background sync starts.

## Rollback

There is no data rollback (the wipe is intentional and there was nothing to keep). If the *deploy*
fails, Kamal keeps the previous image and you can re-run `bin/kamal deploy` after fixing the cause;
the DB is already fresh either way.

## After cutover

The 2.0 is deploy-and-forget: keys are managed in the admin UI (encrypted in the DB), no `.env` edits
or redeploys to add/change a key. Remaining 2.0 work (User-column slim, editorial-source opt-in, the
new mobile-first design) ships incrementally on top.
